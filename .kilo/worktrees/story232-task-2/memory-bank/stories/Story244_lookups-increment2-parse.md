# Story244: Lookups Increment 2 — Parse (Grain Support)

## Goal

Extend the parsing phase for lookup declarations to support the optional `grain` clause. When present, the grain clause specifies one or more measure names (comma-separated) whose types must be `Interval`-derived, making the lookup temporal (data varies by time and concept dimensions). When absent, the lookup is timeless.

This story extends the grammar (`CPLLookups.g4`), data structures (`ParserLookupDefinition`), and listener (`LookupsListener`) to recognize, parse, and store grain clause information. No cross-reference validation is performed at the parser level; all grain measure existence and type validation is deferred to the analysis phase (Story245).

This story is part of [Epic006: CPL Lookups Implementation](../../epics/Epic006_cpl_lookups-implementation.md) and is Increment 2 of the 5-increment lookups strategy defined in [ERO006 — Lookups Incremental Implementation](../specifications/design/cpl/eros/ERO006_lookups-incremental-implementation.md).

## Test-First Development

This story follows the Logical TDD Lifecycle. For each coding task, tests are written before or alongside the implementation to confirm correctness. Grammar tests verify the ANTLR parser accepts valid grain syntax and rejects malformed input. Struct tests verify zero-value defaults for new fields. Listener tests verify the full flow from parse tree to populated `ParserLookupDefinition`. The test-and-implement cycle is integrated within each task rather than broken out as separate tasks.

## Constraints

- No cross-reference validation at the parser level: grain measure names are stored as raw strings. All existence and type validation is deferred to analysis (Story245).
- `HasGrain` must be distinct from `len(Grain) > 0`: a grain clause with zero measures (which is an analysis-phase error) must produce `HasGrain=true, Grain=[]`, while absence of a grain clause produces `HasGrain=false, Grain=nil`.
- Backward compatibility: lookups without grain clauses must continue to parse correctly. Existing tests from Story241 must pass unmodified.
- `indent` tokens enforce readable indentation but do not define scope boundaries.
- All file paths in task descriptions are relative to `source_root` (`src/chronocone_planning_language`).

## Intent

### Task 1: Extend grammar with grain clause

Add the `grainClause` grammar rule and make it optional in `lookupDeclaration` so the ANTLR-generated parser recognizes `grain` keyword syntax in lookup declarations. The GRAIN lexer token is expected to already exist in the lexer grammar. Verify and regenerate ANTLR Go files so downstream listener code can reference the generated context types.

### Task 2: Extend ParserLookupDefinition with grain fields

Add `Grain []string` and `HasGrain bool` fields to the `ParserLookupDefinition` struct so the listener can store parsed grain data. These fields use Go zero values for backward compatibility — lookups without grain clauses default to `HasGrain=false, Grain=nil`.

### Task 3: Update LookupsListener for grain extraction

Modify `ExitLookupDeclaration` to check for the optional grain clause and extract measure names when present. The extraction pattern mirrors the existing dimensions and celltype extraction code. Set `HasGrain=true` whenever the grain clause is present in source, even with zero measures.

### Task 4: Create parse_and_analyze_only examples with grain

Provide example CPL files exercising grain syntax: valid temporal lookups with one or more grain measures, and edge cases (empty grain, non-existent measure names) that the parser accepts but the analysis phase will later catch.

## Acceptance Criteria

1. `CPLLookups.g4` grammar accepts optional `grain` clause with one or more comma-separated measure names between `dimensions` and `celltype` clauses
2. Grammar tests pass for: single grain measure, multiple grain measures, no grain clause (backward compatibility)
3. `ParserLookupDefinition.Grain` is populated with raw measure names when grain clause is present in source
4. `ParserLookupDefinition.HasGrain` is `true` when grain clause is present (including empty clause), `false` when absent
5. Listener tests pass for all grain scenarios: present (single/multiple measures), absent, empty clause
6. Lookups without grain clauses continue to parse correctly; existing Story241 tests pass unmodified
7. No grain type validation is performed at the parser level (deferred to analysis)
8. `parse_and_analyze_only/` examples with grain parse correctly

## Notes

- The `GRAIN : 'grain';` lexer token is expected to already exist in `ChronoconePlanningLanguageLexer.g4` (added for connector grain declarations). Task 1 includes a verification step rather than assuming it is absent.
- `Grain` is stored as `[]string` (not a single string) because the grammar allows comma-separated measure names. The analysis phase validates that each name references a valid measure with an `Interval`-derived type.
- A grain clause with zero measures (`grain` keyword followed by nothing on the same line) is syntactically valid at the parser level and sets `HasGrain=true, Grain=[]`. The analysis phase (Story245) reports this as a validation error.
