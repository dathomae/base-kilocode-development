# Epic005: CPL Metrics Implementation

## Title

CPL Metrics Implementation

## Ultimate Goal

Implement the complete metrics functionality for the CPL compiler across all processing phases — parsing (ANTLR grammar), analysis (semantic validation and CIL generation), and synthesis (Go code generation). Metrics define calculated time series with inputs, formulas, and conditional logic. The implementation follows the 8-increment top-down approach defined in ERO005, with each increment producing a working end-to-end executable (parse → analyze → synthesize) that reads CPL, IO spec, and data, then outputs computed metric values.

### Parallelism Notes

- Increments 4, 5, 6, and 7 are independent of each other (each extends different aspects of the grammar/analysis) and can potentially be developed in parallel after Increment 2 completes.
- Within each increment, the synthesize story depends on its corresponding parse-analyze story.

Stories from other epics may be interleaved with these stories. Specifically, **Story161_parquet-test-utility.md** from Epic004 provides the parquet test data generation needed for testing metrics increments.

## Constraints

1. Each increment must produce a working end-to-end executable (parse → analyze → synthesize) with test data
2. Later increments must not break functionality from earlier increments
3. All phases must align with the existing CPL phase architecture (parse → analyze → synthesize)
4. Follow the [Logical TDD Lifecycle](../../concepts.md#logical-tdd-lifecycle) (BTDD) for all coding stories
5. Parser changes require corresponding ANTLR grammar updates; follow the [ANTLR Listener Organization Convention](../../lessons-learned.md#antlr-listener-organization-convention) — one listener file per grammar file
6. Expression rules live in the root grammar (`ChronoconePlanningLanguage.g4`) since they are shared across CPL constructs (metrics, unit/measure conversions, future aggregators/spreaders); metrics-specific rules live in `CPLMetrics.g4`
7. Parse/analysis separation must be maintained: the parser captures syntax only; the analyzer performs semantic validation
8. Follow the [Symbol Table-Driven Parsing Pattern](../specifications/patterns/symbol-table-driven-parsing.md) — push/pop scope tables during parsing, define symbols in current scope, attach parse-context data to `SymbolDefinition.Data`, walk symbol table tree during analysis to assemble declarations
9. Follow the [Postfix Expression Parsing Pattern](../specifications/patterns/postfix-expression-parsing.md) — parser pushes operands/operators in postfix order; analysis evaluates the postfix sequence to build CIL trees
10. Data structures evolve incrementally — fields are added only in the increment that implements them, not pre-declared. Go zero values provide sensible defaults for unused fields
11. Types are initially represented as `float64`; detailed type selection (fixed-point, overflow detection, `math/big`) is deferred to the [Type Selection](../specifications/design/cpl/type-selection.md) design
12. Lookup support is deferred to a future design/ERO; the `lookup` keyword is recognized by the lexer but lookup resolution is not implemented
13. Each story must include working examples with CPL files, IO specifications, and test data
14. Generated code must use the [`CILAbstractTransformer`](../specifications/design/cpl/go-synthesis-target/synthesis.md#cilabstracttransformer) infrastructure for CIL tree walking
15. Generated code must follow the Setup/Compute/Cleanup lifecycle defined in the synthesis design

## Acceptance Criteria

1. All stories in the epic are marked as Completed
2. Each increment produces a working executable that reads CPL, IO spec, and data, then outputs computed metric values
3. All parser stories implement the grammar features defined in [ERO005_metrics-parsing-phase.md](../specifications/design/cpl/go-parser-target/eros/ERO005_metrics-parsing-phase.md)
4. All analyzer stories implement the validation and CIL tree construction defined in [ERO005_metrics-analysis-phase.md](../specifications/design/cpl/go-analysis/eros/ERO005_metrics-analysis-phase.md)
5. All synthesizer stories generate appropriate Go code as defined in [ERO005_metrics-synthesis-phase.md](../specifications/design/cpl/go-synthesis-target/eros/ERO005_metrics-synthesis-phase.md)
6. Increment 8 produces multi-metric executables with topological evaluation order, dead-code elimination, and full IO specification integration for dimensional/temporal configuration
7. All stories include comprehensive unit tests following BTDD practices
8. Parse/analysis separation is maintained throughout — no semantic validation in the parser
9. Cross-references to metrics, dimensions, lookups, and measures are validated during analysis
10. Documentation is updated to reflect which features are available at each increment

## Notes

- **Superseded Stories**: Existing stories Story106 (`cpl-parser-metrics`), Story107 (`cpl-metric-data-structure-design`), and Story108 (`cpl-metric-evaluation`) predate the ERO005 design and use different patterns (AST-based types, separate data structure design). These are superseded by the incrementally-structured stories in this epic and should be moved to canceled-stories or archived.
- **Lookup Support**: The `lookup` input kind keyword is recognized by the lexer but full lookup implementation is deferred to a future design/ERO. Short form name resolution includes the lookup precedence step but will not resolve to lookups until they are implemented.
- **Type Selection**: Numeric types initially use `float64`. Fixed-point arithmetic, overflow detection, and `math/big` integration are deferred to a separate design — see [type-selection.md](../specifications/design/cpl/type-selection.md) and the [Fixed-Point Arithmetic Pattern](../specifications/patterns/fixed-point-arithmetic.md).
- **Dimension Indexing**: Dimension indexing on input refs (e.g., `order_lead_time[product]`) is deferred to a future increment/ERO.
- **Aggregator/Spreader Integration**: Will require additional EROs once basic metrics are implemented.
- **Test Parquet Utility**: Story161 from Epic004 provides the parquet test data generation utility used by metrics increments.
