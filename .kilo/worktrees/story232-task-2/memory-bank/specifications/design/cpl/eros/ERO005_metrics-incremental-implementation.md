# ERO005: Metrics Incremental Implementation

## Title

Metrics Incremental Implementation

## Purpose/Goal

Define the incremental approach for implementing metrics functionality across all CPL phases (parsing, analysis, synthesis), detailing the minimal functionality needed to support metric declarations with inputs and calculations, with each increment producing a working end-to-end executable.

## Decision Status

Draft

## Implementation Status

Not Yet Implemented

**Related Epics:**

- [Epic005_cpl-metrics-implementation.md](../../../epics/Epic005_cpl-metrics-implementation.md)

## Context

### Situation

Metrics are a fundamental building block of the CPL. They define calculated time series with inputs, formulas, and conditional logic. The metrics implementation must span all three CPL phases: parsing (syntax recognition via ANTLR grammar), analysis (semantic validation and CIL tree generation), and synthesis (generation of executable Go code). Each increment must produce a working end-to-end executable that can process CPL files with accompanying IO specifications and test data.

To avoid overwhelming complexity, an incremental approach is required that focuses on minimal functionality in early increments and builds toward the full metrics specification.

### Constraints

- The implementation must integrate with the existing ANTLR-based parser infrastructure
- Must follow the [Symbol Table-Driven Parsing Pattern](../../../patterns/symbol-table-driven-parsing.md) for parsing
- Must follow the [Postfix Expression Parsing Pattern](../../../patterns/postfix-expression-parsing.md) for expression handling
- Parse/analysis separation must be maintained: the parser captures syntax only; the analyzer performs semantic validation
- Each increment must produce a working executable (parse → analyze → synthesize) with test data
- Types are initially represented as `float64` (detailed type selection design is deferred to [type-selection.md](../type-selection.md))

### Requirements

- Parse `metrics` sections and metric declarations with `inputs` and `calculate` sub-declarations (see [metrics-syntax.md](../../requirements/cpl/metrics-syntax.md))
- Build raw `ParserMetricDefinition` structures stored in `SymbolDefinition.Data` during parsing
- Walk the symbol table tree during analysis to assemble `AnalysisMetricDefinition` entries
- Generate one CIL tree per metric and one single-node CIL tree per connector
- Walk CIL trees to generate executable Go code via the standard tree walker
- Support IO specifications for output metric selection, dimensional configuration, and compute architecture (see [io_specs.md](../../requirements/cpl/io_specs.md))

### Assumptions

- Concepts, types, units, measures, and connectors are already implemented (Epics 001-004 provide the foundation)
- The ANTLR grammar can be extended with a `CPLMetrics.g4` grammar file
- Expression parsing uses the postfix approach: parser pushes operands/operators to definitions; analysis evaluates the postfix sequence to build CIL trees
- CIL tree walking infrastructure can be reused from existing connector synthesis
- Each increment can use a test parquet file generated by the existing parquet test utility

## Evaluation Criteria

1. **End-to-End Completeness** (High importance): Each increment must produce a working executable that reads CPL, IO spec, and data, then outputs computed metric values.
2. **Incremental Value** (High importance): Each increment must add usable functionality; no increment should be purely scaffolding.
3. **Parse/Analysis Separation** (High importance): The parser must not perform semantic validation; all cross-references and dependency resolution must happen in analysis.
4. **Consistency** (Medium importance): Data structures and patterns should evolve consistently with the existing concepts, types, units, and connectors implementations.
5. **Testability** (Medium importance): Each increment must include working examples with CPL files, IO specifications, and test data.

## Options Considered

Three approaches were evaluated. **Bottom-up** (expression first) was rejected because early increments would produce no working end-to-end system. **Parallel phase** (all features at once) was rejected due to overwhelming complexity and violation of the established incremental pattern. **Top-down** (metric structure first, with a trivial `calculate` returning `0` in Increment 1) was selected because it produces a working end-to-end pipeline immediately, exercising parse → analyze → CIL generation → CIL walk → synthesis from the very first increment, with each subsequent increment adding a specific, testable feature. This mirrors the successful approach used for concepts, types, units/measures, and connectors.

## Decision

**Chosen Option:** Option 2 - Top-Down Implementation (Metric Structure First)

**Rationale:**
The top-down approach delivers a working end-to-end pipeline in the very first increment: a CPL file with metric declarations, inputs, and a trivial `calculate` clause is parsed, analyzed, and synthesized into a Go executable that processes input data and produces output. This validates the entire pipeline architecture immediately and provides a foundation for incremental feature addition.

Each subsequent increment adds a specific feature (arithmetic, conditionals, aliases, time shifting, short form, IO spec integration) while maintaining the working pipeline. The expression infrastructure grows organically — Increment 1 requires only a literal node handler in the CIL walker, and each new expression type adds a new handler.

This approach mirrors the successful pattern used for concepts (ERO001), types (ERO002), units/measures (ERO003), and connectors (ERO004).

## Implications

### Positive Implications

- Working end-to-end pipeline validated in Increment 1, reducing architectural risk
- Each increment produces a demonstrable, testable result
- Expression handling can be built incrementally alongside metric structure
- Consistent with the existing incremental implementation pattern across all CPL components
- CIL tree walking infrastructure is exercised and validated early

### Negative Implications / Trade-offs

- Early increments produce trivial calculations (e.g., always return `0`), which provides limited demonstration value until Increment 2
- Expression infrastructure (postfix evaluation, operator handling) must be built across multiple increments rather than all at once
- Data structures evolve incrementally: fields for aliases, where clauses, and backward/forward are added only in the increment that implements them, not pre-declared
- Increment 8 (IO spec integration) is needed before multi-metric executables can be generated with full dimensional/temporal configuration

### Future Considerations

- Detailed type selection (fixed-point, overflow detection, `math/big`) is deferred to a separate design document — see [type-selection.md](../type-selection.md) and the [Fixed-Point Arithmetic Pattern](../../../patterns/fixed-point-arithmetic.md)
- Lookup support is deferred to a future design/ERO; the current design acknowledges lookups in input declarations but defers implementation
- Aggregator and spreader integration will require additional EROs once basic metrics are implemented

## Notes

### Increment Sketches

Each increment is end-to-end across parse → analyze → CIL generation → CIL walk → synthesize. Every increment produces a working executable with test data. See [Metrics Design](../metrics-design.md) for full increment descriptions.

**Increment 1: Basic Metric Declarations with Identity Calculation**

- _Parser:_ New `CPLMetrics.g4` grammar file with `metricsSection`, `metricDeclaration`, `inputs` block (metric/dimension names only, no `as`/`where`/`backward`), and `calculate` clause accepting the literal `0`. New `MetricsListener` that pushes `ParserMetricDefinition` onto the symbol table on `ExitMetricDeclaration`, pushes input reference definitions on `ExitInputRef`, and pushes a literal `0` operand definition on `ExitLiteral`.
- _Analyzer:_ New `AnalyzeMetricsScope` function registered with `WalkSymbolTable`. Assembles `AnalysisMetricDefinition` entries from parser definitions. Generates one CIL tree per metric with a single `CILLiteral(0)` node. Generates one single-node CIL tree per connector.
- _Synthesis:_ CIL tree walker handles `CILLiteral` nodes (emits constant). Connector CIL trees walk to Arrow parquet read code. Generated Go executable returns `0` for each metric cell.

**Increment 2: Simple Arithmetic in Calculate with IO Specification Acceptance**

- _Parser:_ Extended grammar for arithmetic expression rules (`+`, `-`, `*`, `/`) with explicit operator rules for listener callbacks. New listener methods push operand definitions (identifiers from Increment 1, numeric/string literals) and operator definitions (`PlusOperatorDefinition`, `MinusOperatorDefinition`, etc.) in postfix order. Parenthesized expressions handled by grammar recursion.
- _Analyzer:_ Postfix evaluation loop: iterate definitions, push operands onto stack, pop operands for operators and create `CILBinaryOp` nodes. Type-check arithmetic operands. Validate all input references exist. Accept and validate full IO specification — verify output metric names exist, store IO spec for synthesis use.
- _Synthesis:_ CIL tree walker handles `CILBinaryOp` nodes, emitting Go arithmetic operators. Emits access code for `CILInputRef` nodes to read input metric data for current cell. Reads IO spec to determine output metrics.

**Increment 3: Tensor Calculation Parallelism**

- _Parser:_ No changes.
- _Analyzer:_ No changes — IO spec already accepted and validated in Increment 2.
- _Synthesis:_ Use compute architecture from IO spec (CPU cores, cache size, memory) to implement tensor calculation parallelism — partition tensor computation across multiple goroutines or CPU cores. This increment is synthesis-only.

**Increment 4: Conditional Expressions**

- _Parser:_ Extended grammar for `if`/`else if`/`else`/`end if` and `when`/`default`/`end when` constructs. Each branch body gets its own child scope in the symbol table (`IfBodyScope`, `ElseBodyScope`, `WhenBodyScope`, etc.). Conditions use the same infix-to-postfix mechanism as arithmetic, with comparison and logical operators (`==`, `!=`, `<`, `>`, `<=`, `>=`, `and`, `or`, `not`) pushed in postfix order. `Nil` literal recognition.
- _Analyzer:_ Postfix evaluation extended with comparison/logical operators and Nil/bool literals. Walk child body scopes to assemble `CILConditional` or `CILWhenClause` nodes. Implement truthiness rules (Nil/false/zero/empty-string = falsy). Validate all branches produce a result.
- _Synthesis:_ CIL tree walker handles `CILConditional` and `CILWhenClause` nodes, emitting Go `if`/`else` blocks.

**Increment 5: Input Aliases and Where Clauses**

- _Parser:_ Extended grammar for `as` alias clause and `where` clause on input declarations. Parse `aspect=ACTUALS`/`aspect=FORECAST` with boolean combinations (`and`, `or`, `not`). Store alias mapping and where conditions in parser definitions.
- _Analyzer:_ Resolve aliases to underlying metric/dimension references. Validate alias uniqueness. Record where-clause aspect filters on resolved input references.
- _Synthesis:_ CIL tree walker emits Go code that uses aliased variable names. Where-clause conditions emit aspect-filtering logic (slice selection by actual/forecast status).

**Increment 6: Time Shifting (Backward/Forward)**

- _Parser:_ Extended grammar for `backward()` and `forward()` clauses on metric inputs. Parse time measure name and shift expression (numeric constants, references). Store shift information in parser input definitions.
- _Analyzer:_ Validate backward/forward time measure references. Support self-references (metric referencing itself via backward/forward alias — creates a time-series dependency, not a cycle). Record time shift offsets on resolved input references.
- _Synthesis:_ CIL tree walker handles `CILTimeShift` nodes, emitting Go code for array index offset calculations (current cell index − shift amount).

**Increment 7: Short Form Metrics**

- _Parser:_ Extended grammar for short form syntax (`<name> = <calculation>`). Convert short form to equivalent long form `ParserMetricDefinition` internally.
- _Analyzer:_ Scan CIL tree for identifier references and resolve each to metric or dimension. Detect name collisions (a name matching both a metric and a dimension is an error). Short form definitions produce identical CIL trees to long form.
- _Synthesis:_ No changes — short form produces identical CIL trees to long form, so the walker is unchanged.

**Increment 8: Full Synthesis with IO Specification Integration**

- _Parser:_ No changes — all syntax already supported.
- _Analyzer:_ Build complete metric dependency DAG in second analysis pass after all definitions are assembled. Walk DAG for topological evaluation order. Detect circular dependencies (excluding time-shifted self-references). Implement dead-code elimination: only include metrics reachable from IO spec outputs.
- _Synthesis:_ Use IO spec for output metrics' dimensions, celltype, grain, and compute architecture. Generate multi-metric Go executables with topological evaluation order. Configure compute parameters (CPU cores, cache size, memory) from IO spec architecture section.
