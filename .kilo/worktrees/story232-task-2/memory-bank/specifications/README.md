This is the specifications directory, which includes sufficient specification of the ChronoCone system to understand its purpose, key features, and overall architectural organization. The specification is organized in a tree structure to provide both connectivity between higher and lower level concepts without repeating material or explanations, and to facilitate the incremental definition of the system.

There are six levels of specification, some of which will be optional for any given feature:

1) **Concepts** ([`concepts.md`](concepts.md)) defines the key concepts implemented by the system. These are the key points to discuss with a potential customer that would cause them to be interested in the system. The terminology should be recognizable by a user of the system.

2) **Requirements** (in the [`requirements/`](requirements/) directory) extend the concepts by specifying lower level items. These include the types and general outline of UI or plugin functionality, reporting, general behavior of agents, and user-perceivable behavior that users might be particularly interested in (data availability, authentication/authorization, performance, sandboxing, metric lifecycle, and so on). Concepts or definitions that exist in [`concepts.md`](concepts.md) SHOULD NOT BE REPEATED, although they may be referenced and the same terms should be used where feasible. The terminology should be recognizable by a user of the system. Requirements documents may be split to facilitate incremental review and use by agents.

3) **Architecture** (in the [`architecture/`](architecture/) directory) captures the overall organization of the system, especially for parts that are potentially longer lived (schema definitions, service division, endpoint definitions). These include major system components and services that could exist in some form in post-v0 versions of the system. Elements are included in the architecture because they provide implementation guidance for things in concepts or requirements. Architecture documents may include terminology not exposed to users or customers; when an internal term maps back to a user-visible term, that mapping should be given explicitly. Like requirements, architecture documents should be broken into logically related pieces to facilitate incremental review and use by agents.

4) **Design** (in the [`design/`](design/) directory) captures decisions that are not general enough for architecture and, in many cases, are specific to one version of the system. Like the levels above, design documents should be broken into bite-sized pieces.

5) **Stories** (in the [`../stories/`](../stories/) directory) capture some element of the concepts, requirements, architecture, or design for implementation. Stories capture what needs to be done at the task level to facilitate implementation by agents.

6) **Ad-hoc engineer decisions or work**. These need not be documented in advance, or may be associated with issues that are not stories. They are decisions that require no coordination with other implementors, will not introduce organizational confusion, and generally are not significant enough to warrant inclusion in any of the other levels.

The philosophy is that description or specification of things to be implemented should stop at the highest level that makes it possible to write a reasonable story whose outcome would not surprise another system implementor in a way that would compromise their work or the product. In theory, some aspect of the system might appear only in concepts and a story, although it is likely that most features or elements of the system have at least some of their aspects discussed at lower levels.

## Guidelines

- The purpose of these various levels of specification is to describe the functionality and organization to a level sufficient that multiple people could work on implementing some version of the system and have their work line up without confusion about functionality, presentation, or system organization.
- Specification should stop at the highest level that will satisfy the above guideline, assuming that a reasonably experienced engineer will be implementing each story.
- Reference, do not repeat, explanations or information that is contained in a higher level specification or that is captured in another form. For example, if database schemas are specified as part of the architecture and captured in SQL files with sufficient comments to understand their relationship and usage, that information need not be repeated in the architecture documents, only referenced when needed.

Each level should be broken into a set of relatively brief, logically organized files with a table of contents captured in a markdown file named `toc.md`. The `toc.md` should consist of a markdown table referencing the file and a brief explanation of its contents.
